# RFC-0023 — Real secp256k1 Point-Addition Workload

| Field | Value |
|---|---|
| Status | Draft (v0.3) |
| Depends on | RFC-0001 (workload pin), RFC-0002 (fixture pipeline), RFC-0015 (proof statement), RFC-0018 (operations equivalence) |
| Supersedes | the v0.2 XOF-derived random gate sampler at `python/grover_tax/gen_fixtures.py::_build_circuit_from_xof` (for v0.3 workload only; v0.2 fixture retained for legacy) |
| Audience | implementers, cryptographic reviewers |

## 1. Summary

Replaces the v0.2 random-1024-gate circuit with the **upstream
`tanujkhattar/zkp_ecc` secp256k1 point-addition gate-net builder**.
v0.3's fixtures `fixtures/v0.3-pointadd-T<i>.json` for `i ∈ {0, 1, 2, 3, 4}`
each carry a deterministically-generated subset of the upstream
point-add circuit at the scale tier `n_g ∈ {1024, 16384, 262144,
1048576, 16777216}` (RFC-0024 §3). The fixture format is otherwise
identical to v0.2 (GTV1 + commitment hashes + test cases). The
prover programs do not change — they read the same `cb` bytes, parse
the same GTV1, and simulate the same gate set.

## 2. Upstream gate-net builder

The upstream `tanujkhattar/zkp_ecc` repository at the pinned
`WORKLOAD.md::upstream_commit` SHA contains a gate-net builder at
`lib/src/sim.rs` (or a Python equivalent in `python/`) that emits a
~17M-gate `Vec<Gate>` realising one secp256k1 point-addition. v0.3
imports this builder via:

1. Add a Python wrapper `python/grover_tax/pointadd_builder.py` that
   either:
   - (a) Calls into the upstream Rust crate via PyO3 bindings (preferred
     if upstream exposes a Python API), OR
   - (b) Re-implements the gate-net builder in pure Python from the
     upstream source. The reimplementation MUST be byte-equivalent to
     a fresh upstream run (verified by `S23-T1`).
2. The builder is **deterministic**: same upstream commit + same RNG
   seed (if any) → same gate list.
3. Pin the builder's output bytes via SHA-256 in `WORKLOAD.md` (new
   row in §2's six-field table — extends RFC-0001 by one field for
   v0.3).

### 2.1 Scale truncation

The full upstream builder emits ~17M gates. For tiers below T4, v0.3
truncates the gate list at `n_g`:

```python
def build_truncated_pointadd_circuit(n_g: int) -> list[Gate]:
    full = upstream_pointadd_builder()
    return full[:n_g]
```

This is **not semantically equivalent to a "smaller point-add"** — a
prefix of the gate list does not realise a smaller secp256k1
operation. The truncation is purely a *workload-scaling* device for
the apples-to-apples comparison. The Stwo and SP1 programs do not
care what `C` realises; they care that they both execute the same
`C` over the same `T`.

RFC-0015's §3 conjunct "C is consistent with the pinned point-add
builder at the WORKLOAD.md upstream_commit" is therefore relaxed for
tiers below T4 to: "C is the first `n_g` gates of the pinned builder".

T4 (full 17M gates) is the only tier at which the proof attests to
the *complete* point-addition circuit.

### 2.2 Test-case generation

For each tier, the v0.3 fixture's `test_cases[]` is generated by:

1. Sample `n_tc = 4` random 256-bit `x_i` from SHAKE-256(SEED) per
   RFC-0002 + RFC-0021 §16.
2. For each `x_i`, compute `y_i = simulate(C_truncated, x_i)` via
   `sim_reference.py`'s v0.2-compatible interpreter.
3. Emit the fixture.

F-INV-4 is then naturally satisfied: `run(C_truncated, x_i) == y_i`
by construction.

## 3. Cryptographic semantics of the truncation

RFC-0015 §3.6's `Φ_v0.2` (= `Φ_v0.3` per SPEC-v0.3.md §2) requires the
prover to prove `simulate(C, x_i) = y_i` for the gate list `C` it
deserialises from `cb`. The truncation operation happens *outside the
proof* (in `pointadd_builder.py` / `gen_fixtures.py`) — the prover
sees `cb` as opaque GTV1 bytes and simulates them.

**This is sound.** The prover is honestly attesting to executing the
gate list it was given. The semantic gap between "truncated upstream
gate list" and "complete upstream point-add" is a *workload* gap, not
a *soundness* gap. It is disclosed in `RESULTS.md`'s scope section
(RFC-0024 §9).

A v0.4 OPEN-Q (`OPEN-Q-v0.4-7`) is whether to embed the upstream-commit
binding inside the proof — i.e., require the prover to prove that
`SHA-256(upstream_builder_at_commit)` reduces to `cb`. This would
close the truncation soundness gap but adds substantial circuit cost
and is out of scope for v0.3.

## 4. Memory bounds + fallback

| Tier | `n_g` | SP1 RSS (est.) | Stwo RSS (est.) | Fits on c3-highmem-22 (176 GiB)? |
|---|---|---|---|---|
| T0 | 1 024 | ~17 GiB | ~5 MiB | yes |
| T1 | 16 384 | ~25 GiB | ~80 MiB | yes |
| T2 | 262 144 | ~50 GiB | ~1.3 GiB | yes |
| T3 | 1 048 576 | ~120 GiB | ~5 GiB | yes for Stwo; marginal for SP1 |
| T4 | 16 777 216 | ~1 600 GiB | ~80 GiB | **NO** for SP1; marginal for Stwo |

(Estimates extrapolated linearly from v0.2 SP1 RSS of 17.1 GiB at
1024 gates; subject to actual measurement at Phase 2.)

**T4 fallback paths:**
1. **Memory-tier upgrade:** `m4-ultramem-160` (3.75 TiB) at ~$24/hr.
   T4 SP1 would cost ~$1 800 per proof. Out of v0.3 budget.
2. **Recursive composition:** Split `C` into `k` segments, prove each
   on its own, recurse. SP1 has native recursion support; Stwo Cairo
   would need a custom composition layer. Research-level; OPEN-Q-v0.4-6.
3. **Skip T4 in v0.3.** Document the OOM bound; report scaling-curve
   extrapolation only at T4. This is the v0.3 default per `SCOPE.md`
   Tier-B.

## 5. Migration from v0.2

v0.2's `fixtures/v0.2.json` is retained at the repo root for backward
compatibility and for the T0 cross-check (RFC-0024 §3.1: T0's ρ should
match v0.2's 2.52× within 5%).

v0.3 fixtures are emitted under `fixtures/v0.3/`:

```
fixtures/
  v0.1.json                  (legacy v0.1, retained)
  v0.2.json                  (legacy v0.2, retained for cross-check)
  v0.3/
    T0-pointadd-1024.json
    T1-pointadd-16384.json
    T2-pointadd-262144.json
    T3-pointadd-1048576.json
    T4-pointadd-16777216.json
```

`gen-fixtures --version v0.3 --tier T2 --out fixtures/v0.3/T2-pointadd-262144.json`
is the entry point per RFC-0002 amended by this RFC.

The fixture-version detection in `validate_schemas.py` (RFC-0021 §16
content-based detection) routes `"version": "v0.3"` to the new
`fixture-v0.3.schema.json`. The schema is identical to
`fixture-v0.2.schema.json` except `version: const: "v0.3"` and an
additional optional field `tier: enum: ["T0", "T1", "T2", "T3", "T4"]`.

## 6. Test obligations

| Test ID | Description | Layer |
|---|---|---|
| `S23-T1` | Upstream builder pin: running the builder at `WORKLOAD.md::upstream_commit` emits a gate list whose SHA-256 matches the pin | crypto-integrity |
| `S23-T2` | F-INV-4 holds on each tier: `run(C_truncated, x_i) == y_i` for all 4 test cases at every tier | fixture |
| `S23-T3` | Truncation determinism: rebuilding the truncated circuit twice from the same upstream commit produces byte-equal `cb` | reproducibility |
| `S23-T4` | T0's `cb` differs from v0.2's `cb` (the v0.3 T0 circuit is the upstream-prefix, not the XOF-random) — but T0's ρ must still match v0.2's within 5% | cross-check |
| `S23-T5` | Schema validates each tier's fixture against `fixture-v0.3.schema.json` | schema |
