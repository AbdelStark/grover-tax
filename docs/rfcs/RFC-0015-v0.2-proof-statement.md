## 1. Summary

This RFC fixes, in normative mathematical language, the public statement `Φ_v0.2` that both the SP1 and Stwo provers prove at v0.2. It replaces the v0.1 statement (point-addition over secp256k1, with `C` as a hidden witness) and the v0.1 MVP intermediate (N modular additions in `F_p`). v0.2's statement is *bit-level gate-circuit execution of a random reversible classical circuit*, with all inputs public.

## 2. Motivation

Three motivations:

1. **Spec-implementation drift.** The actual SP1 and Stwo v0.2 programs (commit `c5fff05`) deserialise `circuit_bytes` and simulate the gates; the corpus formally describes a different statement (point-addition). A reviewer reading the corpus cannot infer the actual claim. (Gap 1.1 of `GAP-ANALYSIS.md`.)
2. **Witness scope.** `circuit_bytes` is *published* in `fixtures/v0.2.json`. The v0.1 language treats `C` as a secret witness; that is no longer the case. We must update the witness boundary so that no security analysis is built on a false premise.
3. **Verifier obligations.** The verifier must check that the proof's public inputs match the fixture, otherwise a substitution attack (Gap 5.3) is undetected. The statement must carry the public inputs in a form a verifier can recompute from the fixture alone.

## 3. Normative statement

### 3.1 Domains

Fix `λ = 100` (bits of conjectured soundness, RFC-0019 §2).

Let:
- `B = {0,1}` (the binary alphabet).
- `B^n` the set of `n`-bit strings, with bit-index `i ∈ [0, n)` and the convention `bit_i(s) = s[i] := (s >> i) & 1` for `s` viewed as an integer in `[0, 2^n)`.
- `F` the set of 8-byte fixed-width gate records (§3.3).
- `G* = ⋃_{k ≥ 0} F^k` the set of all finite gate sequences.

### 3.2 Hash functions

- `H_SHA256 : B^* → B^256` is SHA-256 (FIPS 180-4).
- `H_BLAKE2s : B^* → B^256` is BLAKE2s with parameter set `(digest_length=32, key_length=0, fanout=1, depth=1, leaf_length=0, node_offset=0, node_depth=0, inner_length=0, salt=0^{64}, personal=0^{64})` as per IETF RFC 7693 §3.1. (We refer to this as the *normalised default* parameter set; RFC-0019 §5.2 pins it byte-precisely.)

### 3.3 Gate encoding (`GTV1`)

A gate record is a tuple `(op, t, a, b) ∈ {0,1,2,3} × ([0, 256) ∪ {0xFFFF})^3` encoded as 8 bytes:

```
byte 0       : op  ∈ {0x00, 0x01, 0x02, 0x03}
byte 1       : 0x00     (reserved; range-check enforces equality)
bytes 2..3   : t   as u16 little-endian
bytes 4..5   : a   as u16 little-endian
bytes 6..7   : b   as u16 little-endian
```

The serialisation `enc_gtv1 : G* → B^*` is

```
enc_gtv1((g_1, ..., g_n_g)) = "GTV1" || n_g_u32_le || enc(g_1) || ... || enc(g_n_g).
```

The parser `parse_gtv1 : B^* → G* ∪ {⊥}` is the inverse defined on inputs of the exact form above and `⊥` otherwise (including any length mismatch, magic mismatch, or out-of-range field). RFC-0016 §4 and RFC-0017 §3 specify `parse_gtv1` byte-precisely; both implementations MUST reject any input the canonical parser rejects.

The validity predicate `valid_gate : F → B` requires:

| `op` | Constraint on `t`, `a`, `b` |
|---|---|
| `NOP` (`0`) | `t ∈ [0, 256), a = 0xFFFF, b = 0xFFFF` |
| `NOT` (`1`) | `t ∈ [0, 256), a = 0xFFFF, b = 0xFFFF` |
| `CNOT` (`2`) | `t ∈ [0, 256), a ∈ [0, 256), a ≠ t, b = 0xFFFF` |
| `TOFFOLI` (`3`) | `t ∈ [0, 256), a ∈ [0, 256), b ∈ [0, 256), a ≠ t, b ≠ t, a ≠ b` |
| else | ✗ (parser must reject before this point) |

The `a ≠ t`, `b ≠ t`, `a ≠ b` clauses are *not* enforced by the prover's circuit at v0.2 (RFC-0016 §6, RFC-0017 §3 note this as an explicit relaxation); they are documentary and enforced only by `gen_fixtures.py`. RFC-0019 §6 explains why this relaxation does not weaken `Φ_v0.2`.

### 3.4 Gate semantics

For `g = (op, t, a, b)` and `s ∈ B^256`:

```
apply_gate(s, g) =
    case op of
        NOP     → s
        NOT     → flip(s, t)                            where flip(s, i)[j] = s[j] ⊕ [j=i]
        CNOT    → s'   where s'[j] = s[j] for j ≠ t,
                       s'[t] = s[t] ⊕ s[a]
        TOFFOLI → s'   where s'[j] = s[j] for j ≠ t,
                       s'[t] = s[t] ⊕ (s[a] ∧ s[b]).
```

For `C = (g_1, …, g_n_g) ∈ G*`:

```
simulate(C, s) = apply_gate(apply_gate(…apply_gate(s, g_1)…, g_{n_g-1}), g_{n_g}).
```

### 3.5 Test cases and public inputs

A *test case* is a pair `(x, y) ∈ B^{256} × B^{256}` interpreted as 32-byte little-endian (bit `i` is byte `i/8` bit `i mod 8`, LSB-first).

The fixture's `x_hex` field is 128 hex chars = 64 bytes. **Only the first 32 bytes are normative input.** The trailing 32 bytes are historical (originally the `Q` half of `(P, Q)` for v0.1's point-addition). v0.2 implementations MUST silently ignore the trailing 32 bytes. v0.3 will narrow the schema to 64-char `x_hex`.

The fixture's `y_hex` field is 64 hex chars = 32 bytes and is the entire normative output.

### 3.6 `Φ_v0.2`

Public input on either side is a tuple

```
Π = (cb, h, n_g, n_tc, T)
```

where `cb ∈ B^*`, `h ∈ B^256`, `n_g, n_tc ∈ ℕ`, and `T = ((x_1, y_1), …, (x_{n_tc}, y_{n_tc})) ∈ (B^{256} × B^{256})^{n_tc}`.

```
Φ_v0.2^{SP1}(Π) := H_SHA256(cb) = h
                ∧ parse_gtv1(cb) = C ≠ ⊥
                ∧ |C| = n_g
                ∧ ∀ i ∈ [1..n_tc]: simulate(C, x_i) = y_i.

Φ_v0.2^{Stwo}(Π) := H_BLAKE2s(cb) = h
                 ∧ parse_gtv1(cb) = C ≠ ⊥
                 ∧ |C| = n_g
                 ∧ ∀ i ∈ [1..n_tc]: simulate(C, x_i) = y_i.
```

`Φ_v0.2` denotes the language `{Π : Φ_v0.2^{SP1}(Π) ∨ Φ_v0.2^{Stwo}(Π)}`. SP1 proves membership under SP1's commitment hash; Stwo under Stwo's. They share all conjuncts except the commitment-binding equation, which is the only intentional cryptographic divergence (RFC-0005, RFC-0019 §5).

### 3.7 Per-side public input anchoring

`Φ_v0.2` involves `(cb, h, n_g, n_tc, T)`. The prover's proof must bind to all five components. The mechanism differs per side:

- **SP1.** `prove.rs` writes `cb`, `n_tc`, and the `(x_i, y_i)` pairs into the zkVM stdin (private). The committed public values are `(commitment, n_tc)` only. To bind the test cases, the v0.2 program MUST also `sp1_zkvm::io::commit` a digest `H_SHA256(cb || n_tc_be || x_1 || y_1 || … || x_{n_tc} || y_{n_tc})` (RFC-0017 §4). The verifier obtains this digest from the proof's public values and re-checks it from the fixture.

- **Stwo.** The bootloader path passes `(cb, expected_commitment, n_tc, (x_i, y_i))` as the task's `user_args_list`. These are committed by the bootloader's program-hash chain (Pedersen) into the bootloader's public input. The verifier recomputes the bootloader's expected public input from the fixture and compares. (RFC-0022 §4.)

Both anchoring mechanisms are normative: a verifier that skips them cannot reject the substitution-of-test-cases attack (RFC-0020 §3.2).

## 4. Witness shape

| Component | Role |
|---|---|
| `cb` | public input on both sides (deserialised inside the proof) |
| `(x_i, y_i)_{i=1..n_tc}` | public input on both sides (asserted inside the proof) |
| `C` (gates parsed from `cb`) | *derived* public input (not separately committed; its hash equals `h`) |
| intermediate states `s_{i, j}` for `i ∈ [1..n_tc], j ∈ [0..n_g]` | private witness on both sides |

No component of `Π` is hidden. v0.2 is a public-coin argument-of-knowledge for an NP statement, not a ZK proof. (RFC-0019 §3.)

## 5. Verifier obligations

A v0.2 verifier MUST:

1. Read `fixtures/v0.2.json`. Extract `cb` (hex-decoded from `circuit_byte_serialisation_hex`), `h_sha = circuit_commitment_sha256_hex`, `h_blake = circuit_commitment_blake2s_hex`, `n_tc`, `T`.
2. Recompute `H_SHA256(cb)` and `H_BLAKE2s(cb)` locally; compare to `h_sha` and `h_blake`. Reject the fixture if either disagrees.
3. Extract `n_g` from `cb[4..8]` (little-endian u32). Reject if `|cb| ≠ 8 + 8·n_g`.
4. Pass the proof to the per-side verifier binary (`sp1-sdk` for SP1; `stwo-cairo verify` for Stwo).
5. Cross-check the public values:
   - SP1: read the proof's committed public values; assert `commitment = h_sha` and the test-case digest equals `H_SHA256(cb || n_tc_be || x_1 || y_1 || … )`.
   - Stwo: recompute the bootloader's expected `program_hash` + `user_args_list` hash; assert it equals the proof's public input.

Exit `0` iff all five checks pass. Otherwise exit `1` with the relevant subcode.

A `bin/apples-verify` binary implementing the five checks is required by RFC-0022 §5.

## 7. Alternatives considered

**A1: keep gate-list as hidden witness (true ZK).** Rejected for v0.2: the cost of keeping `cb` hidden inside SP1 (rebuild zkVM stdin path to opening a separately committed digest) and inside Stwo (load `cb` from witness, not public input) is design surface we declined for the first apples-to-apples-on-real-statement milestone. `OPEN-Q-v0.3-1` keeps this on the roadmap.

**A2: prove a real secp256k1 point-addition.** ~17 M gates upstream; outside the 30-minute clean-clone budget on a c3-standard-8. Deferred to v0.3 + multi-core / multi-rig protocols. `OPEN-Q-v0.3-2`.

**A3: prove `Σ_i simulate(C, x_i) ⊕ y_i = 0^{256}` instead of `simulate(C, x_i) = y_i`.** Saves nothing — the test still requires running `simulate` `n_tc` times — and obscures the read of the spec. Rejected.

**A4: include `n_g` as a top-level fixture field, not derived from `cb[4..8]`.** Adds a redundancy check but introduces a new F-INV (n_g matches cb header). Out of scope for v0.2; RFC-0021 §15 keeps the schema additive only.
